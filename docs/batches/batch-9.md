## Мета
Memora надійна й безпечна перед тим, як нею користуватиметься хтось, крім власника:
помилки ловляться автоматично, а не власником на телефоні.

## Задачі
1. **CI (GitHub Actions):** на кожен push і PR — `lint`, `typecheck`, `test`, `build` (без
   секретів). Authenticated smoke у CI — **лише якщо** власник додасть GitHub secrets: опиши
   в цьому чаті, які саме (назви), і зроби job, що пропускається без них. Секрети сам не
   вводь і не виводь. Безкоштовні хвилини Actions — врахуй (кеш pnpm, без зайвих матриць).
2. **Перевірка БД після міграцій:** скрипт, який знаходить у спільній БД функції/в'ю, що
   посилаються на неіснуючі об'єкти (пачка 7 видалила `get_streak`, а `get_progress_stats`
   ще її викликав — «Прогрес» на проді падав). Запуск — частина ритуалу після міграції
   (додай у `CLAUDE.md`).
3. **Моніторинг помилок:** серверні й клієнтські помилки мають бути видні без власника.
   Порівняй безкоштовні варіанти (напр. власна таблиця + маршрут з rate-limit і без
   персональних даних vs Sentry free vs логи Vercel), обери, поясни в журналі рішень.
   Межа помилок (`error.tsx`) показує людське повідомлення і відправляє звіт.
4. **Фінальна ревізія безпеки:** RLS на всіх таблицях (кожна політика проти сценарію
   «чужий користувач»), усі server actions і маршрути перевіряють користувача й allowlist,
   ліміти розміру вхідних даних, rate-limit AI, `service_role` лише на сервері, заголовки
   безпеки й **nonce-CSP** (відкладено з пачки 0), `pnpm audit` (виправити high/critical).
   Знахідки — список у roadmap §2.5 зі статусом.
5. **a11y і продуктивність:** Lighthouse mobile для `/`, `/app`, `/app/practice` (a11y без
   критичних; performance — виправити очевидне, без переписування); клавіатурна навігація
   практики (Enter/Tab/фокус), контраст, підписи кнопок-іконок.
6. **Прибирання:** тимчасові файли (`scripts/.sect-tmp.mjs`, `scripts/.shots-tmp.mjs`),
   мертвий код/залежності (`knip` або еквівалент — лише очевидне, без ризикових змін).

## БД
Міграції — тільки через Supabase CLI, як у `CLAUDE.md` («Supabase і Vercel»), у
`begin; … commit;` + запис у `schema_migrations`; MCP `apply_migration` не використовувати.
Прод ділить цю БД: зміни сумісні з кодом `main`; видалення — окрема cleanup-міграція після
merge. **Перед будь-яким `drop` — перевір залежності в самій БД, а не лише grep по файлах.**
Після міграцій — advisors (MCP), скрипт із задачі 2, gen types.
